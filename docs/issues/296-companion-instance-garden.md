# #296 — 정확한 동물 개체 UUID 기준 정원 배치

- 백엔드 V34는 기존 각 정원 슬롯에 **원래 디자인의 가장 먼저 보유한 개체 UUID**를 백필한다. 기존 x/y 좌표, 슬롯, 디자인 ID, 배경은 유지한다.
- `garden_placements.instance_id`를 NOT NULL 및 유저·디자인과 조합 FK로 강제한다. 동일 디자인이라도 **서로 다른 UUID**이면 슬롯 최대 다섯 개에 배치 가능.
- 기존 `GardenUpdate.Placement(slot,designId,x,y)` 형식도 허용. 구버전 클라이언트의 배치는 같은 디자인 1개 제한을 유지하며, 기존에 배치된 UUID가 있으면 이를 계속 사용한다.
- 새 클라이언트는 `instanceId`를 함께 보낸다. 서버가 소유권/디자인/중복 UUID/최대 5개를 검사한다. 다른 사용자의 UUID는 403.
- `GET /api/v1/companions/me/garden` 및 PUT 응답의 각 placement에는 `instanceId`가 포함된다. `GET /api/v1/companions/me/instances/garden`은 인덱스 PK 조인으로 각 슬롯의 정확한 개체만 읽는다.
- 기존 디자인 기준 판매도 **배치된 UUID는 보호**, 성장·돌봄 경험이 있는 개체는 판매하지 않는다. 기존 재고 수량·가격·뽑기 결과는 변경하지 않는다.
- 프론트에서는 기존 캐릭터 표시/모션 디자인을 유지하면서 배치 키는 UUID가 된다. 5마리 모두 화면에서 이동하더라도 이동 중 서버 요청 없음. 실제 저장은 디바운스된 최대 다섯 슬롯 PUT.
- 홈의 최신 성장 수치와 선택 동물 UUID를 서버 API 응답으로만 표시한다.

## 성능/안전
- DB 읽기: `garden_placements(user_id,slot)` 0~5건 및 `companion_instances(id)` PK 인덱스 조인.
- DB 쓰기: 정원 PUT 시 슬롯 최대 5개. 미션/포인트/카탈로그 등 전량 API 다시 조회하지 않음.
- 동시성: 정원 PUT, 뽑기, 판매는 기존 사용자 계정 락으로 직렬화. 진화/돌봄도 소유 UUID 행 락을 유지. 낙관적 정원 version 충돌 방지.
- V34 마이그레이션 전후 사용자별 배치 개수, UUID 중복 수, 재고 수량을 검증해야 함.
- 운영 p95 성능 측정/부하 테스트는 별도 이슈 #297. 신기능은 develop에서 QA 후 main 릴리스.

## 알려진 구형 앱 제약
구형 앱은 placement의 UUID를 저장하지 않으므로 동일 디자인 복수 배치를 표시하지 못한다. 구형 앱이 저장하면 복수 배치가 하나로 축약될 수 있어, 실제 배포 전에 **호환성/버전 강제 업데이트 정책을 검토**한다.
